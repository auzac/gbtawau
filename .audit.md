# Production Architecture Audit — GBT Church App

**Sources**: `.map.md` (static structure) + `.execution.md` (runtime behavior)
**Principle**: Where they conflict, `.execution.md` is authoritative.

---

## 1. Architectural Reality Classification

### Structural Claim (.map.md)

The structure suggests a **layered SPA**: Infrastructure/Config → Data Access (`lib/supabase.js`) → State Management (AuthContext, LocaleContext) → UI (8 page components). Route-level separation with a shared Supabase client singleton. The directory tree implies modularity — `lib/`, `contexts/`, `pages/`, `components/`.

### Runtime Truth (.execution.md)

The system is a **page-driven monolith with embedded service calls**. Every page is a self-contained mini-application that:

- Independently fetches its own data on mount (`useEffect → supabase → useState`)
- Independently mutates data (`supabase.insert/update/delete → loadAll() → setState`)
- Independently re-implements shared logic (isMobile detection, loading spinners, toast notifications, modal shells, Google Fonts injection)
- Has zero awareness of other pages' data state
- Unmounts entirely on navigation away, losing all local state

There is no service layer. `lib/supabase.js` is an 11-line configuration export — not a data access layer. There is no shared business logic. There is no inter-component communication. What `.map.md` labels as "Layer 2: Data Access" is a single `createClient()` call. What it labels as "Layer 3: State Management" is two thin React contexts totaling ~77 lines.

**Classification**: **Tightly-coupled UI-data execution mesh** — each page directly embeds Supabase queries inside React lifecycle hooks, directly embeds mutation logic inside click handlers, and directly drives re-renders from raw database responses. Pages are not "consumers of a data layer" — they are the data layer, the business logic, and the UI, all fused into single files of up to 1174 lines.

## 2. Structure vs Runtime Mismatch Analysis

### Mismatch 1: Modular Structure, Monolithic Execution

**.map.md** shows: 8 route-level pages, 2 contexts, 1 lib file — clean horizontal separation.
**.execution.md** reveals: Every staff page duplicates identical patterns:

| Pattern | Duplicated In |
|---|---|
| `isMobile` check + resize listener | StaffHub, MemberManager, ContentManager, FinanceManager (LandingPage uses different breakpoint) |
| Toast notification + 2.5s auto-dismiss | MemberManager, FinanceManager, ContentManager |
| ModalShell + overlay click-to-close | MemberManager, ContentManager |
| Loading spinner + "Loading…" text | All 8 pages |
| `handleLogout = async () => { await signOut(); navigate('/login') }` | StaffHub, MemberManager, ContentManager, FinanceManager |
| Google Fonts `<link>` injection | 6 pages |

The `src/components/` directory exists and is empty. The code has no shared abstractions despite pervasive duplication.

### Mismatch 2: "Data Access Layer" Is a Configuration Export

**.map.md** positions `src/lib/supabase.js` as Layer 2 (Data Access).
**.execution.md** shows: It is 11 lines — `createClient(url, key)` — with zero abstraction. Every page writes raw `supabase.from('table').select('*').eq(...).order(...)` calls directly in event handlers and useEffect callbacks. There is no intermediary, no query builder, no response normalization, no error transformation.

### Mismatch 3: Route Independence Masks Deep Data Coupling

**.map.md** shows: 8 independent routes, each rendering one page component.
**.execution.md** reveals: LandingPage and ContentManager are tightly coupled through shared Supabase tables (`verse_library`, `events`, `carousel_items`, `roster`). They independently fetch identical datasets with nearly identical queries. Changes in ContentManager are invisible to LandingPage until manual browser refresh. Structurally they appear decoupled; at runtime they are coupled through the database but lack any synchronization mechanism.

### Mismatch 4: "State Management Layer" Is a Pass-Through

**.map.md** describes AuthContext and LocaleContext as "Layer 3: State Management."
**.execution.md** shows: AuthContext is a 44-line wrapper around two Supabase SDK calls (`getSession()` + `onAuthStateChange()`). It adds no transformation, validation, role-based access, or session expiry handling. LocaleContext stores one string in localStorage and provides a key-lookup function. Neither constitutes a "state management layer" in any architectural sense — they are configuration providers.

## 3. Data Flow & Execution Inefficiencies

### 3.1 Mutation → Full Reload Anti-Pattern

Every CRUD operation follows an identical destructive cycle:

```
Mutation (INSERT/UPDATE/DELETE)
  → loadData()
    → SELECT * FROM table (entire dataset)
      → setState(allData)
        → Full component re-render
          → All useMemo recomputations
```

**Concrete costs from execution traces:**

| Operation | HTTP Requests Triggered |
|---|---|
| Add 1 member | 1 INSERT + 1 `SELECT * FROM members` |
| Delete 1 event | 1 DELETE + **5 SELECT queries** (ContentManager.loadAll refetches verse_library ×2, events, roster, carousel_items) |
| Record 1 payment | 1 INSERT + 2 SELECT queries (members + renewals) |
| Activate 1 verse | 2 UPDATEs + **5 SELECT queries** |
| Reorder 1 carousel item | 2 UPDATEs + **5 SELECT queries** |

### 3.2 Redundant Cross-Page Query Multiplication

The `events` table is queried **3 times independently** with the same `.gte('date', today)` filter:
1. LandingPage: `SELECT * FROM events WHERE date >= today` (full rows)
2. ContentManager: `SELECT * FROM events WHERE date >= today` (full rows — identical dataset)
3. StaffHub: `SELECT count FROM events WHERE date >= today` (count only — same filter, different column selection)

The `verse_library` active verse query (`WHERE is_active = true`) runs **2 times independently**: LandingPage and ContentManager.

None of these share a cache, a context, or a deduplication mechanism.

### 3.3 O(n²) Client-Side Computation Patterns

**FinanceManager.hasPaidForYear()**: Not memoized. Called for every member in `stats` computation and again for every member in `filteredMembers` computation. In a 500-member church:
- `stats.paid` = 500 calls to `hasPaidForYear()`
- `filteredMembers` sort = 500 more calls
- Each call is `renewals.some(...)` = O(n) scan of all renewals
- Total: 500 × 500 = 250,000 array element checks per render

This recomputes on every payment recording, every year change, every search keystroke, and every status filter click.

**MemberManager**: Every keystroke in search triggers synchronous recomputation of `filteredMembers` (iterates all members, checks 3 fields each) and `stats` remains stable (depends only on `members`, not filters). No debounce — 5 keystrokes/sec = 5 full recomputation passes/sec.

### 3.4 N+1 and Sequential Query Chains

**Verse CSV Import**: Each row gets an individual `supabase.insert()` — N rows = N sequential HTTP requests. `.execution.md` explicitly notes this is "NOT batch" unlike member import.

**generateCode()**: Up to 10 sequential Supabase queries checking for code collisions. `.execution.md` notes: "VERY RARE WORST CASE: 10 round-trips to Supabase."

**LyricsSession join**: Session lookup executes 3 sequential queries (`public_sessions` → `session_songs` → `songs`) instead of a single Supabase query with nested selects or a database view.

### 3.5 No Pagination — Unbounded Data Loading

Every page loads full tables on mount:
- MemberManager: `SELECT * FROM members` — no LIMIT
- LyricsSession: `SELECT * FROM songs` — no LIMIT
- ContentManager: `SELECT * FROM verse_library`, `SELECT * FROM carousel_items` — no LIMIT
- LandingPage: `SELECT * FROM roster` — ALL roster records, no date filter

For a church with years of roster data or a large song library, these queries grow unbounded.

## 4. State Lifecycle Problems

### 4.1 Login Race Condition

`.execution.md` §3 Phase C documents this explicitly:

> navigate('/staff') fires immediately after successful supabase call. But onAuthStateChange may not have fired yet. If getSession() was called during initial AuthProvider mount and returned null (because user wasn't logged in then), the AuthContext still has user=null. [...] ProtectedRoute sees user=null and redirects to /login, then onAuthStateChange fires → user set → but user is already at /login.

The code relies on Supabase SDK firing `onAuthStateChange` synchronously or near-synchronously after `signInWithPassword`. This is an implementation detail of the SDK, not a guaranteed contract. No explicit guard exists.

### 4.2 Verse Activation Gap Window

`.execution.md` §5 (Verse CRUD) identifies a two-step non-transactional activation flow:

```
UPDATE verse_library SET is_active = false WHERE is_active = true  -- Step 1: deactivate
UPDATE verse_library SET is_active = true WHERE id = X              -- Step 2: activate
```

Between Step 1 and Step 2, **no verse is active**. If LandingPage queries during this window, `loadActiveVerse()` returns null and the about section shows a translated fallback string. The gap duration is one HTTP round-trip.

### 4.3 Cross-Page Data Staleness

`.execution.md` §6.3:

> Changes in ContentManager do NOT propagate to LandingPage: No shared state, No event bus, No Supabase realtime subscriptions, No React context for content data. User must manually refresh browser.

The same staleness exists between FinanceManager and StaffHub: recording a payment updates FinanceManager's local state but StaffHub's pending count remains stale until the user navigates back to `/staff` (which triggers a fresh mount + fetch).

### 4.4 Auth Rehydration Timing Dependency

Every protected route renders a spinner until `getSession()` resolves. On slow connections or Supabase latency spikes, users stare at spinners. There is no timeout, no retry, no degraded experience. The `loading` state is a binary gate.

### 4.5 Unmount Data Loss on Navigation

`.execution.md` §7.5:

> If user has an open "Add Member" form and navigates away: Form state and modal state are lost. No "unsaved changes" warning. No navigation guard (useBlocker, beforeunload).

All page-level state (form inputs, modal visibility, selected items, search terms, filter selections) is destroyed on navigation because the component unmounts.

### 4.6 Duplicated Effect Chains on Mount

Every staff page fires these effects on mount:
1. `useEffect(() => { isMobile check + resize listener }, [])` — 5 identical implementations
2. `useEffect(() => { load data from Supabase }, [])` — same pattern, different tables
3. Multiple `useState` initializations (LandingPage: 14; ContentManager: 15+; MemberManager: 9)

The isMobile duplication means 5 independent `resize` event listeners exist simultaneously when navigating between pages (though only the active page's listener matters).

## 5. Coupling Map

### 5.1 Hidden Coupling: ContentManager ↔ LandingPage (Database-Mediated)

**Structure says**: Two independent pages at different routes (`/staff/content` vs `/`).
**Execution reveals**: They share 4 data tables (`verse_library`, `events`, `carousel_items`, `roster`) with **zero synchronization**. ContentManager writes; LandingPage reads stale data. This is a **distributed state consistency problem** masked as route separation.

### 5.2 Hidden Coupling: FinanceManager ↔ StaffHub (Same Pattern)

**Structure says**: Independent pages (`/staff/finance` vs `/staff`).
**Execution reveals**: Both query `membership_renewals` and `members` tables. StaffHub derives a "pending renewals" count that becomes stale the moment FinanceManager records a payment. The dashboard badge is a snapshot frozen at navigation time.

### 5.3 Duplicated Logic Coupling (Identical Code, Separate Execution)

Every staff page independently implements:
- `handleLogout` (identical 2-line function)
- `isMobile` responsive detection (identical useEffect + resize listener)
- Toast notification system (identical state + setTimeout pattern)
- Modal overlay click-to-close (identical `onClick` on backdrop div)
- Loading spinner (identical JSX structure, different color tokens)

These are "pattern clones" — structurally independent but execution-identical. Any change to the pattern (e.g., changing toast duration) requires editing 4+ files.

### 5.4 Direct Supabase Coupling (Every Page → Singleton)

Structure shows `lib/supabase.js` as a shared dependency — a legitimate singleton pattern.
Execution reveals: All 8 pages + AuthContext import and use `supabase` directly with raw query strings. There is no query abstraction, no typed interface, no validation layer. A schema change to `events.date` column would require finding and updating raw `.gte('date', ...)` calls across 3 files. A rename of `membership_renewals` table breaks queries in 2 files.

### 5.5 LocaleContext Isolation

`LocaleContext` is consumed **only** by `LandingPage`. All staff pages contain hardcoded English strings. The bilingual infrastructure exists but is coupled to a single consumer, making it de facto a LandingPage utility rather than a system-wide i18n layer.

## 6. Supabase Runtime Pattern Issues

### 6.1 Query Frequency & Redundancy

On a typical user session navigating LandingPage → StaffHub → ContentManager:

- `events` table queried 3 times (LandingPage, StaffHub count, ContentManager) — all with identical date filter
- `verse_library` active verse queried 2 times (LandingPage, ContentManager)
- `carousel_items` queried 2 times (LandingPage active only, ContentManager all)
- `roster` queried 2 times (LandingPage all, ContentManager recent 4)

**Total wasted queries per session**: ~5 redundant HTTP requests. This is inherent in the "every page fetches its own data" architecture.

### 6.2 Mutation Patterns That Create Instability

**Non-transactional multi-write operations:**

| Operation | Writes | Transactional? | Risk |
|---|---|---|---|
| Verse activation | 2 UPDATEs | No | Gap window with no active verse |
| Carousel reorder | 2 UPDATEs | No | Transient duplicate display_order possible |
| Session create | 1 INSERT + 1 batch INSERT | No | Orphaned `session_songs` if second INSERT fails after first succeeds |
| Member bulk import | 1 batch INSERT | Yes (single statement) | Atomic — no risk |

### 6.3 Missing Patterns

**No realtime subscriptions**: Supabase supports realtime via WebSockets. The app uses zero subscriptions. LandingPage never learns about ContentManager changes unless the user refreshes.

**No Row Level Security awareness**: The app uses the anon key for all operations. `.execution.md` traces no RLS-dependent branching. There is no distinction between what the anon key can do vs what an authenticated user can do at the query level.

**No request retry or timeout handling**: Every `await supabase.from(...)` is a fire-and-hope call. Network failures surface as uncaught promise rejections or generic error toasts. There is no retry logic anywhere.

**No optimistic updates**: Every mutation waits for the network response, then issues a full refetch, then renders. The UI feels laggy because it's always waiting for a round-trip before showing results.

### 6.4 Count Queries Waste

StaffHub issues `count: 'exact', head: true` for events and members — efficient in isolation. But LandingPage and MemberManager independently fetch the full rows of those same tables. The count query exists solely because no shared data context exists to derive it from already-fetched data.

## 7. Cross-System Execution Chains

### 7.1 Auth → Route Guard → Page Load Chain

```
AuthProvider.getSession() [async, ~200-2000ms]
  → loading: true (spinner)
  → getSession() resolves [user | null]
  → loading: false
  → ProtectedRoute re-evaluates
    → null → Navigate to /login
    → object → Page mounts
      → useEffect fires → Supabase data queries
```

This is a **strictly sequential chain with a single async gate**. The entire protected area of the app is blocked behind one HTTP request (getSession). There is no progressive rendering, no skeleton UI, no cached auth state reuse.

### 7.2 Locale → LandingPage Chain

```
toggleLocale()
  → setLocale(newLocale)
  → localStorage.setItem
  → document.documentElement.lang = ...
  → LocaleProvider re-render
  → LandingPage re-render (sole consumer)
  → ~40 t() calls re-evaluate
  → Roster month labels re-format
```

This chain is **isolated and low-risk** — single consumer, synchronous flow, no network calls. The only architectural note is that the i18n infrastructure is heavier than its single-consumer reality warrants.

### 7.3 ContentManager Mutation → Public Site Staleness Chain

```
ContentManager.saveEvent()
  → supabase.insert('events', payload)
  → loadAll() [5 queries, ContentManager state updated]
  → ❌ LandingPage NOT notified
  → ❌ No realtime subscription
  → ❌ No shared cache invalidation
  → User sees old events on LandingPage until manual refresh
```

This is the most architecturally significant cross-system chain. It means **the admin interface and public website operate on divergent views of the same data**. Every content change creates a consistency gap that only a browser refresh closes.

### 7.4 LyricsSession Create → Join Chain

```
handleCreate()
  → INSERT public_sessions (get id)
  → BATCH INSERT session_songs
  → navigate('/lyrics/join/CODE')
  → useParams detects urlCode change
  → useEffect fires → loadSession(CODE)
    → SELECT public_sessions
    → SELECT session_songs
    → SELECT songs
```

This is a **tightly-coupled 5-step chain with 5 HTTP requests in sequence**. The create flow makes 2 writes, then the join flow makes 3 reads. Between the two phases, another user could theoretically join the session before the creator's navigation completes.

### 7.5 Token Expiry → Force Logout Chain

```
JWT expires
  → Supabase SDK attempts TOKEN_REFRESHED
    → Success: silent user object update, no UI change
    → Failure: SDK emits SIGNED_OUT
      → AuthContext: setUser(null)
      → ProtectedRoute: user=null → Navigate to /login
      → User is mid-task on a staff page
      → Abrupt redirect, all unsaved work lost
```

No session extension prompt. No "your session is about to expire" warning. No graceful re-authentication modal. Just an immediate redirect.

| R14 | **No debounce on search inputs** — MemberManager and FinanceManager re-filter entire datasets on every keystroke | Low | §7.4 Hotspot 2 |

---

### Risk Concentration Map

The risks cluster around three root architectural characteristics:

1. **Page-as-application pattern** (R1, R4, R9, R10, R13): Because every page is a self-contained data island, state cannot flow between them, data is repeatedly re-fetched, and navigation destroys context.

2. **No data layer abstraction** (R1, R2, R3, R5, R8): Direct Supabase calls in UI event handlers mean no transactional boundaries, no error normalization, no retry logic, and no shared cache.

3. **Missing React infrastructure** (R6, R7, R10): No error boundaries, no navigation guards, no suspense boundaries — the app relies entirely on React's default error propagation and component lifecycle.
