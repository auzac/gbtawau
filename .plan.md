# Architecture Migration Plan — GBT Church App

**Sources**: `.map.md` (structure), `.execution.md` (runtime), `.audit.md` (diagnosis)
**Phase 3 Output**: Controlled, incremental transformation roadmap

---

## 1. Target Architecture Model

### Current Reality (from .audit.md)

```
Page-driven monolith with embedded service calls
  → Each page is a self-contained mini-application
  → Direct Supabase queries in event handlers and useEffect
  → No shared component library (src/components/ empty)
  → Duplicated patterns across 4-8 files
  → No data layer abstraction
```

### Target: Feature-Based Modular SPA

Preserve the React + Vite + Supabase stack. Do not introduce Redux, Next.js, tRPC, or any new framework. The transformation is purely about **reorganizing existing code into modules with defined boundaries**.

| Dimension | Current | Target |
|---|---|---|
| Page structure | Monolithic files (1174 LOC max) | Feature directory with decomposed sub-components |
| Data access | Raw supabase calls in every component | Service module per domain |
| Shared UI | Duplicated inline | Reusable components in /components/ |
| Shared hooks | 5 copies of isMobile, etc. | Extracted hooks in /hooks/ |
| Routing | All routes in App.jsx | Feature-ownable route modules |
| Contexts | Two thin providers | Preserved, not expanded |
| Navigation state | Lost on every page transition | Layout wrapper preserves shell |

### What Does NOT Change

- React 18, Vite, Supabase, Tailwind CDN — same stack
- All route paths — same URLs
- All data query behavior — same filters, ordering, response handling
- Auth flow — same Supabase session management
- Locale flow — same JSON translation files
- All existing files remain intact during migration (additive, not destructive)

## 4. Step-by-Step Migration Plan

### Step 1 — Zero-Risk UI Component Extraction

**Goal**: Populate `src/components/ui/` with pure presentational components extracted from inline code.

**What changes**:
- Extract `LoadingSpinner` from the repeated spinner pattern in all 8 pages
- Extract `Modal` from LandingPage, MemberManager, ContentManager (overlay + click-to-close + animation)
- Extract `Toast` notification component + `useToast` hook state management
- Extract `Badge` from MemberManager/ContentManager/FinanceManager
- Extract `StatCard` from StaffHub/MemberManager/FinanceManager
- Extract `SearchInput` from MemberManager/FinanceManager

**What must NOT change**:
- No behavioral changes — these are pure render components
- No state logic changes — extraction is mechanical (copy JSX + props interface)
- Existing inline code remains temporarily (components are used in parallel with old inline code, then swapped)

**Risk level**: LOW
- Pure presentational extraction
- Each extraction independently verifiable (component renders identically to inline version)
- Old inline version can coexist until swap is tested
- Rollback: delete component file, revert import

**Dependency constraints**: None. Can be done in any order. Parallel-safe.

**Verification**: Visual diff — each page looks identical before and after swap. No network behavior changes.

---

### Step 2 — Shared Hook Consolidation

**Goal**: Eliminate duplicated pattern implementations across staff pages.

**What changes**:
- Extract `useIsMobile` from 5 independent implementations (StaffHub, MemberManager, ContentManager, FinanceManager, LandingPage)
- Consolidate `useToast` state management (MemberManager, FinanceManager, ContentManager use near-identical patterns)

**What must NOT change**:
- Breakpoint threshold (768px) preserved at 768px
- Toast auto-dismiss duration preserved at 2500ms
- All existing resize listener cleanup behavior preserved

**Risk level**: LOW
- Pure extraction — no behavioral changes by design
- Each hook replaces 3-5 copies of identical logic
- Old code can be removed after new hook is verified in each consumer

**Dependency constraints**: Independent of Step 1. Both steps 1 and 2 can run in parallel.

**Verification**:
- Resize to 767px → mobile layout renders for all staff pages
- Resize to 768px+ → desktop layout renders for all staff pages
- Toast auto-dismisses at exactly 2500ms in MemberManager, FinanceManager, ContentManager

---

### Step 3 — Service Layer Introduction

**Goal**: Decouple data access from UI by moving all direct Supabase queries into `src/services/` modules.

**What changes**:
- Create `services/supabase.js` (identical to `lib/supabase.js` — or move the file)
- Create `services/members.js` — all member queries
- Create `services/events.js` — all event queries
- Create `services/content.js` — verse, carousel, roster queries
- Create `services/finance.js` — renewal queries
- Create `services/lyrics.js` — session and song queries
- Pages import service functions instead of calling `supabase.from(...)` directly

**Service function contract**: Each service function preserves the exact query signature from .execution.md:

- `getMembers()` — `supabase.from('members').select('*').order('name')`
- `getActiveVerse()` — `supabase.from('verse_library').select('*').eq('is_active', true).maybeSingle()`
- `getUpcomingEvents()` — `supabase.from('events').select('*').gte('date', today).order('date').order('time')`
- `getCarouselItems(activeOnly)` — conditional `.eq('is_active', true)` wrapping
- `createMember(payload)` — `supabase.from('members').insert(payload)`
- (all remaining queries from .execution.md ...)

**What must NOT change**:
- Query filter, ordering, limit behavior — identical
- Response handling pattern — services return `{ data, error }` exactly as Supabase does
- Error handling in pages — callers still handle errors identically
- Refetch patterns — `loadAll()` still calls multiple service functions in parallel
- Auth context — still imports `supabase` client directly for auth operations
- No backend changes, no schema changes

**Risk level**: MEDIUM
- Import path changes in 8 page files + AuthContext
- Risk of incorrect function signature if service interface doesn't match query behavior
- Mitigation: Each service function is a direct wrapper around a `supabase.from(...)` chain. No transformation, no normalization — pure pass-through.

**Dependency constraints**: Must happen after Steps 1-2 (if you're changing import paths, do it after extraction so you only change them once). But can technically be done independently.

**Migration sub-steps**:
1. Create `services/` directory with `supabase.js`
2. Create each domain service file (empty initially)
3. Move one query at a time from a page to its corresponding service file
4. Verify page still works after each query migration
5. After all queries migrated, update all import paths
6. Remove `src/lib/supabase.js` in final cleanup

**Verification**: Every page loads the same data it loaded before. Every mutation writes the same data. The Supabase network tab shows identical query patterns.

---

### Step 4 — Feature Modularization

**Goal**: Reorganize pages into feature directories with decomposed sub-components. This is the largest structural change.

**What changes**:
- `src/pages/LandingPage.jsx` → `src/features/public-home/` with 8 sub-components
- `src/pages/MemberManager.jsx` → `src/features/members/` with 5 sub-components + hook
- `src/pages/ContentManager.jsx` → `src/features/content/` with 6 sub-components + hook
- `src/pages/FinanceManager.jsx` → `src/features/finance/` with 3 sub-components + hook
- `src/pages/LyricsSession.jsx` → `src/features/lyrics/` with 2 sub-components + hook
- `src/pages/StaffHub.jsx` → `src/features/dashboard/` with 1 sub-component
- `src/pages/Login.jsx` → `src/features/auth/Login.jsx`
- `src/pages/AdminTools.jsx` → `src/features/admin-tools/AdminTools.jsx`
- `src/App.jsx` imports updated to point to feature entries

**What must NOT change**:
- Exported component names (feature entries export the same component name as before)
- Route definitions remain in App.jsx (feature entry points match old page file contracts)
- State management remains local to the feature entry (orchestrator pattern)
- Refetch-on-mount behavior preserved
- All existing data flows preserved exactly

**Decomposition principle**: The feature entry file ("index.jsx" or the main `XxxManager.jsx`) keeps the state orchestration and data fetching via service calls. Sub-components are pure or minimally stateful render components that receive props.

**Non-decomposition principle**: Do NOT create sub-components for sections that are rendered < 20 lines or are called once. The goal is to break 1000+ line files into manageable sections, not to atomize every div.

**Risk level**: MEDIUM
- Large file reorganization creates import churn
- Risk of missed import in decomposed files
- Risk of broken context references if sub-components aren't in correct provider scope
- Mitigation: Each feature is migrated one at a time. After each feature migration, the app is tested before proceeding.

**Dependency constraints**: Requires Step 3 completion (service layer must exist so features import from services, not from other features).

**Migration sub-steps**:
1. Create feature directory structure (all empty files)
2. Migrate smallest features first: auth, admin-tools, dashboard
3. Migrate medium features: finance, lyrics
4. Migrate large features: content, members
5. Migrate public-home (LandingPage — largest, 1174 LOC) last
6. Update App.jsx imports to point to feature entries
7. Remove `src/pages/` directory after all features migrated

**Verification**:
- Each route renders the same content as before
- Each CRUD operation completes identically
- Network tab shows same Supabase queries
- No regressions in previously migrated features

**What changes**:

- Mobile/Desktop branching — StaffLayout handles the isMobile check internally

**Risk level**: LOW-MEDIUM

- Main risk: if StaffLayout accidentally wraps or styles content differently
- Mitigation: Visual comparison before/after

**Dependency constraints**: Requires Step 2 (useIsMobile hook) and Step 4 (features exist). Order relative to Step 4: can be done as part of Step 4 or as a separate cleanup.

### Step 6 — Auth Guard Stabilization (Optional)

**Goal**: Fix the login race condition identified in .audit.md R2 without changing auth architecture.

**What changes**:
- Add a `sessionChecked` ref or additional state in ProtectedRoute that waits for getSession() to resolve AND for onAuthStateChange to fire at least once after signIn

**What must NOT change**:
- AuthContext provider structure unchanged
- getSession() and onAuthStateChange pattern preserved
- ProtectedRoute component preserved
- signOut behavior unchanged

**Risk level**: MEDIUM
- Auth flow is fragile (race condition exists)
- Changes to auth timing could introduce regression
- Mitigation: Only modify if the race has been observed in production. Otherwise, document and defer.
- Marked as OPTIONAL — defer until after all structural changes are validated

**Dependency constraints**: Must be last. Auth touches every protected page. Structural changes must be stable before auth timing is modified.

### Extraction Pattern for Each Component

1. **Copy** the inline JSX into a new component file under `components/` or `features/X/components/`
2. **Define** an explicit props interface (no implicit context or closure dependencies)
3. **Import** the component in the originating file
4. **Replace** the inline JSX with a `<Component {...props} />` call
5. **Test** visual and behavioral equivalence
6. **Delete** the old inline code (may be deferred to allow rollback)

### Dependency Risks

| Component | Depends On | Risk if Extracted Wrong |
|---|---|---|
| Modal | Click-outside handler | Modal fails to close; user cannot dismiss |
| Toast | setTimeout cleanup | Memory leak if component unmounts before timeout |
| MemberForm | Form field mappings (DD/MM/YYYY ↔ YYYY-MM-DD) | Date corruption |
| BulkImportModal | Character-by-character CSV parser | Import failure or data corruption |
| DonutChart | SVG percentage math | Visual discrepancy in financial reports |

## 6. Data Layer Evolution Plan

### Phase 1: Service Wrapper Creation (Step 3)

```
Goal: Move raw supabase.from('table') calls from pages into service modules.
Constraint: Preserve exact query behavior. No transformations. No caching.

Execution:
  1. Create /services/ directory
  2. Copy supabase.js from /lib/ to /services/ (both coexist during migration)
  3. For each domain (members, events, content, finance, lyrics):
     a. Read all queries from the page file (from .execution.md traces)
     b. Create service functions that mirror exact query chains
     c. Import service in page file, replace direct supabase calls
     d. Test
  4. After ALL pages migrated: remove src/lib/supabase.js
  5. Update imports in AuthContext.jsx (still needs supabase client)
```

### Service Function Contract

Every service function follows this pattern:

```javascript
// Pattern — exact query preserved, no transformation
export const getFunctionName = async (params) => {
  let query = supabase.from('table').select('col1, col2')
  if (filter) query = query.eq('field', filter)
  if (orderField) query = query.order('field', { ascending: true })
  return await query
}
```

Return signature is `{ data, error }` — identical to direct Supabase SDK returns. Pages handle errors the same way they do now.

### What Service Layer Does NOT Do

- No request deduplication (caching can be added later)
- No data transformation (raw Supabase response preserved)
- No optimistic updates
- No error transformation (Supabase errors pass through unchanged)
- No pagination abstraction (raw queries preserved)

### Post-Migration Enhancement Opportunities

These are NOT part of the mandatory migration but become possible after the service layer exists:

- **`hasPaidForYear()` optimization**: Move from O(n²) client-side scan to a single aggregated Supabase query (or a database view)
- **generateCode() optimization**: Replace 10 sequential collision checks with a single stored procedure call
- **loadAll() granularity**: Refetch only the affected table instead of all 5 datasets
- **Cross-page invalidation**: Add a lightweight event emitter or Supabase realtime subscription in the service layer so LandingPage re-fetches when ContentManager changes data

| System | Risk | Reason |

## 8. Risk-Controlled Execution Strategy

### What Can Break Easily

| Failure Mode | Where | Mitigation |
|---|---|---|
| Missing import after file move | Feature decomposition | Each feature migrated independently; test after each |
| Wrong query filter in service wrapper | Service layer creation | Service functions are direct wrappers. No logic added. |
| Modal fails to close | Component extraction | Verify overlay click and X button behavior per extraction |
| Form date format breaks | MemberForm extraction | DD/MM/YYYY ↔ YYYY-MM-DD conversion must match exactly |
| Toast fires but doesn't dismiss | useToast extraction | Verify setTimeout 2500ms is preserved |

### What Must Be Migrated Last

1. **LandingPage** (1174 LOC) — largest file, public-facing, no room for error. Decompose last.
2. **ContentManager tab system** — cross-tab state is tightly coupled. Decompose as a unit.
3. **AuthContext** — do not modify until structural migration is complete and tested.
4. **App.jsx route definitions** — update last after all feature directories exist.

### Where Temporary Duplication Is Acceptable

- Old inline code can coexist with extracted components during Step 1
- `src/lib/supabase.js` and `src/services/supabase.js` coexist during Step 3
- Old `src/pages/` directory and new `src/features/` directory coexist during Step 4
- Removal of old files is the FINAL action in each step

### Rollback-Safe Boundaries

Each step should be a single git commit with a clear rollback path:

```
Step 1 commit: "extract shared UI components"
  → Rollback: git revert <hash> (pure additive + swap, no data loss)

Step 2 commit: "consolidate shared hooks"
  → Rollback: git revert <hash> (swap back to inline code)

Step 3 commit: "introduce service layer"
  → Rollback: git revert <hash> (revert import changes, services remain as dead files)

Step 4 commit per feature: "migrate X to feature module"
  → Rollback: git revert <hash> (swap App.jsx import back to pages/X.jsx)
```

### Safe Testing Checkpoints Between Steps

| Checkpoint | Verification |
|---|---|
| After Step 1 | Every page renders identically. Spinners, modals, toasts, badges match baseline. |
| After Step 2 | Resize behavior identical. Toast timing identical. Both staff and public pages. |
