# Repository Overview

A single-page web application for **Gereja Baptis Tawau** (GBT Church, Tawau, Sabah, Malaysia). The project serves dual purposes: a public-facing church website with event listings and service rosters, and a password-protected internal staff portal for managing members, content, finances, and worship sessions. Built with Vite + React 18, backed by Supabase (PostgreSQL + Auth), styled with Tailwind CSS via CDN, and deployed on Vercel.

- **Repo name**: `gereja-baptis-tawau` (from `package.json`)
- **Type**: Vite SPA (no SSR, no API routes in repo — all backend logic lives in Supabase)
- **Language**: JavaScript (JSX), JSON
- **Primary dependencies**: `react`, `react-dom`, `react-router-dom`, `@supabase/supabase-js`, `@splidejs/splide`, `lucide-react`
- **Dev dependencies**: `vite`, `@vitejs/plugin-react`, `tailwindcss`, `autoprefixer`, `postcss`
- **Deployment**: Vercel (`vercel.json`), output directory `dist/`, all routes rewritten to `/` (SPA fallback)
- **Current branch**: `main` (clean working tree, 5 commits)

# Core Entry Points

### 1. `index.html` — HTML Shell
- Loads Tailwind CSS from CDN (`cdn.tailwindcss.com`)
- Mount point: `<div id="root">`
- Script entry: `<script type="module" src="/src/main.jsx">`
- Contains inline `<style>` block (currently empty, available for overrides)

### 2. `src/main.jsx` — JS Entry Point
- Imports `React`, `ReactDOM`, `App`, `LocaleProvider`
- Renders `<LocaleProvider><App /></LocaleProvider>` into `#root` inside `<React.StrictMode>`
- No service worker, no error boundary, no analytics

### 3. `src/App.jsx` — Root Component & Router
- Wraps everything in `<BrowserRouter><AuthProvider><AppRoutes /></AuthProvider></BrowserRouter>`
- Defines `ProtectedRoute` — checks `useAuth().user`; shows spinner while loading, redirects to `/login` if unauthenticated
- Route table:

| Path | Component | Auth Required |
|---|---|---|
| `/` | LandingPage | No |
| `/login` | Login | No |
| `/staff` | StaffHub | Yes |
| `/staff/members` | MemberManager | Yes |
| `/staff/content` | ContentManager | Yes |
| `/staff/admin` | AdminTools | Yes |
| `/staff/finance` | FinanceManager | Yes |
| `/lyrics/*` | LyricsSession | No |

### 4. `vite.config.js` — Build Configuration
- Vite 5 with `@vitejs/plugin-react`
- No custom aliases, no environment prefix override, no proxy config

### 5. `vercel.json` — Deployment Configuration
- Framework: `vite`
- Build command: `npm run build`
- Output directory: `dist`
- SPA rewrite rule: all paths rewrite to `/`

# Key Data / Control Flows

## Authentication Flow

```
1. User navigates to /staff (or any /staff/* route)
2. App.jsx → ProtectedRoute checks AuthContext
3. AuthContext:
   a. On mount: supabase.auth.getSession() → sets user (or null), sets loading=false
   b. Subscribes to onAuthStateChange → updates user on login/logout events
4. If loading=true → show spinner
5. If user=null → <Navigate to="/login">
6. If user exists → render child route component
7. Login page: onSubmit → supabase.auth.signInWithPassword(email, password)
   a. Success → navigate('/staff')
   b. Error → setError(message)
8. Logout: handleLogout() → signOut() from AuthContext → supabase.auth.signOut() + setUser(null) → navigate('/login')
```

## Data Fetching Flow (Supabase)

All page components follow the same pattern:

```
1. useState([]) for data arrays
2. useState(true) for loading flag
3. useEffect(() => { loadData() }, [])  — or useCallback for refreshable loads
4. Inside loadData:
   a. supabase.from('table').select('*').[filters].[order]()
   b. On success: setState(data)
   c. On error: setToast/console.error
   d. setLoading(false)
5. Component renders:
   a. Loading state: spinner
   b. Empty state: message + action button
   c. Data state: table/cards/list
```

There is no caching layer, no react-query/SWR, no optimistic updates. Every mutation (insert/update/delete) calls `loadData()` again to refetch.

## UI Composition Flow

```
main.jsx
  └─ LocaleProvider           ← wraps everything, provides t() and toggleLocale()
      └─ App                  ← BrowserRouter
          └─ AuthProvider      ← wraps routes, provides user/signOut
              └─ AppRoutes    ← <Routes> with all route definitions
                  ├─ LandingPage   ← public, uses both contexts + direct supabase queries
                  ├─ Login         ← public, uses supabase.auth directly
                  ├─ LyricsSession ← public, uses supabase tables directly
                  ├─ StaffHub      ← protected, uses useAuth() + supabase
                  ├─ MemberManager ← protected, uses useAuth() + supabase
                  ├─ ContentManager← protected, uses useAuth() + supabase
                  ├─ AdminTools    ← protected, placeholder
                  └─ FinanceManager← protected, uses useAuth() + supabase
```

All protected pages import `useAuth` for the signOut function. All pages import `supabase` directly from `lib/supabase.js` for data operations. The `useLocale` hook is used only by `LandingPage` — staff pages are English-only (hardcoded strings).

## Locale / i18n Flow

```
1. LocaleProvider initializes locale from localStorage (default 'bm')
2. translations = { bm: {...}, en: {...} } loaded from JSON files
3. t(key) = translations[locale][key] || key  (falls back to key string)
4. toggleLocale() swaps bm↔en, writes to localStorage, sets <html lang="...">
5. Used only in LandingPage — all other pages contain hardcoded English strings
```

## Lyrics Session Flow

```
Creating:
  1. User clicks "New Session" → generateCode() creates random 4-digit code
  2. User selects songs, sets expiry (1/2/4/8 hours)
  3. Creates session: INSERT public_sessions (code, expires_at)
  4. Links songs: INSERT session_songs for each selected song
  5. Navigates to /lyrics/join/:code

Joining:
  1. User enters 4-digit code (or arrives via /lyrics/join/:code URL)
  2. loadSession(code): SELECT public_sessions WHERE session_code = code
  3. Validates not expired
  4. SELECT session_songs WHERE session_id = session.id
  5. SELECT songs WHERE id IN (linked song_ids)
  6. Displays one song at a time with prev/next navigation
```

# Architectural Notes (Observations, Not Judgments)

- **No shared component library**: `src/components/` is empty. Each page re-implements its own modal shells, button styles, badges, stat cards, form inputs, and toast notifications. Design tokens (colors, fonts) are redefined per-file as constant objects.
- **Inline styles**: All styling is done via inline `style={{}}` objects. Tailwind classes are used in a few places (Login.jsx, AdminTools.jsx, LoadingPage spinner) but most files use 100% inline styles with token constants.
- **No external CSS files**: There are zero `.css` files in the project. Tailwind is loaded via CDN in `index.html` but underutilized. No PostCSS/Tailwind build pipeline is configured despite `tailwindcss`, `autoprefixer`, and `postcss` being in devDependencies.
- **No TypeScript**: All files are `.jsx` or `.js`. The `@types/react` and `@types/react-dom` devDependencies are present but unused.
- **No testing**: No test files, no test framework in dependencies.
- **No error boundaries**: React errors will crash the component tree.
- **No environment validation at runtime**: supabase.js throws if env vars are missing at import time, but no fallback UI.
- **Tailwind CDN**: Using `<script src="https://cdn.tailwindcss.com">` in production. The CDN version processes classes at runtime in the browser (heavier and slower than the build-time JIT compiler).
- **CSV import/export**: MemberManager manually parses CSV with character-by-character logic (handling quoted fields). FinanceManager and ContentManager use simpler split-based CSV generation.
